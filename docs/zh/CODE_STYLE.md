# AgentOrbis 代码规范

**语言：**[English](../CODE_STYLE.md) | 简体中文

这份规范用于保持项目易读、易维护，并让中文使用者能顺畅理解代码背后的业务规则。提交代码前请遵循以下约定。

## 语言与命名

- 项目介绍、开发文档、Issue 和 Pull Request 使用中文，常见技术名词可保留英文。
- 代码标识符（模块、类、函数、变量、数据库字段和 API 字段）使用清晰的英文名称，避免拼音和含义不明的缩写。
- Python 代码使用类型标注；异步 I/O 路径保持异步，不要在事件循环中执行阻塞操作。
- 命名应表达业务含义。例如优先使用 `conversation_id`、`request_id`，避免 `id1`、`data2` 这类无法说明用途的名称。

## 可读性与结构

- 一个函数或类只承担清晰、有限的职责；将复杂流程拆成能体现业务步骤的小函数。
- 先选择直接、容易跟踪的控制流。避免不必要的层级、隐式副作用、过度通用的框架和重复的配置入口。
- 让业务规则留在领域/应用层；HTTP、数据库和外部服务细节放在相应的适配层。
- 共享状态和数据库写入要明确可见；涉及事务、并发、幂等和租户隔离时，应让约束能从代码和测试中追踪。
- 遵循仓库的 Ruff 配置和现有格式。不要为单个模块引入与项目约定冲突的格式化规则。

## 中文注释与文档字符串

- 新增或修改的代码注释、模块说明和公开函数/类的文档字符串使用中文。
- 注释解释“为什么这么做”、业务含义、边界条件或不明显的并发/兼容性约束；不要把代码逐行翻译成中文。
- 对状态转换、权限判断、幂等处理、事务边界、外部副作用等关键逻辑，用简短中文注释说明不变量或风险点。
- 简单且自解释的代码不需要强行添加注释。优先通过更好的命名和结构表达意图。
- 修改现有代码时，如触及注释或文档字符串，应顺手将其更新为准确的中文；不要为了本规范进行无关的大范围注释改写。

## 错误处理与安全

- 对可预期的业务失败使用明确的错误类型和稳定的 API 响应；不要用宽泛的异常捕获掩盖错误。
- 日志和诊断信息不得包含密码、令牌、数据库连接串或客户敏感信息。
- 密钥从环境配置读取，不写入源码、测试快照或示例命令中的真实值。
- 对外部副作用设置超时，并在重试前确认操作是否幂等；失败恢复策略要有测试或文档依据。

## 测试与验证

- 新增业务行为或修复缺陷时，增加能验证行为和边界条件的测试；测试名称应说明场景和预期结果。
- 领域逻辑尽量保持可离线测试。依赖真实 MySQL、Redis 或 API 的验证应与快速离线测试明确区分。
- Pull Request 描述应写明运行过的检查和暂未覆盖的场景。
