# 意图分类体系 v1

**语言：**[English](../INTENT_TAXONOMY.md) | 简体中文

目录版本：`1.0`。代码定义见 [`intent_registry.py`](../../backend/src/agentorbis/domain/intent_registry.py)。

## 范围与落地状态

本文件定义 AgentOrbis 的业务意图、对话动作和分类边界。注册目录已实现，可查询正式 ID 和当前 API 别名；它提供元数据，不执行路由、工具或外部业务。

当前 API、模型输出契约、提示词、策略和前端已采用正式业务 ID，解释结果包含 `taxonomy_version: "1.0"`。解析历史语义时接受 `refund`、`logistics`、`policy_qa` 别名，并统一输出正式 ID。任务类型仍为 `refund`、`logistics`；咨询焦点的 kind 仍为 `policy_qa`，intent 为 `policy.consult`。这些状态字段不等同于业务意图。MySQL、真实业务工具和多 Agent 路由仍待实现。

## 分类层次

| 层次 | 职责 | 示例 |
|---|---|---|
| 业务意图 | 用户的业务目标 | `refund.apply` |
| 对话动作 | 用户如何推进已有或新目标 | `answer_pending`、`correct` |
| 实体与目标 | 本轮明确参数及所指任务 | 订单 A100、已有退款任务 |
| 对话策略 | 结合状态选择任务、补问或生成操作计划 | 给退款任务填订单号 |
| 能力编排 | 选择具备权限和能力的工具或 Agent | `logistics.tracking` |

一条消息可以包含多个动作，每个动作分别记录原文依据、参数、任务指向及歧义。意图名称不能直接作为外部执行授权。

## 已支持的业务目录

| 正式 API ID | 兼容输入别名 | 用户目标 | 必填任务参数 | 能力声明 |
|---|---|---|---|---|
| `refund.apply` | `refund` | 办理退款申请 | `order_id`、`reason` | `refund.application` |
| `logistics.track` | `logistics` | 查询订单物流 | `order_id` | `logistics.tracking` |
| `policy.consult` | `policy_qa` | 咨询电商售后规则 | 无固定任务槽位 | `policy.retrieval` |

退款必填参数遵循当前实现，后续可以随业务版本调整。参数齐全只表示 `ready`，不代表退款已提交。能力声明只表示未来所需能力，不代表工具已可用。

政策问题保留完整问题作为检索输入。`refund_timeline`、`return_policy`、`shipping_fee` 等可作为后续可选 topic，不需要每个 FAQ 都新增业务意图；当前实体契约还没有 topic 字段。

## 对话动作目录

保留现有 ID，避免仅因命名习惯重写提示词和评测。

| ID | 定义 | 核心限制 |
|---|---|---|
| `start_task` | 提出新的业务目标 | 明确新业务不能被旧待回答问题覆盖 |
| `answer_pending` | 补充参数或回答澄清 | 必须能确定回答的目标；候选选择不能猜 |
| `correct` | 更正信息 | 只提取当前消息中的新值 |
| `resume` | 继续旧任务或澄清 | 多个合理候选时先问用户 |
| `cancel` | 请求放弃当前办理流程 | 不等同于撤销已提交的真实退款 |
| `ask_question` | 政策或规则咨询 | 不覆盖正在办理的任务 |
| `confirm` | 确认明确的候选或操作 | 必须绑定具体待确认对象 |
| `reject` | 否定候选或提议 | 否定某订单不自动取消别的任务 |
| `other` | 尚无明确动作归类 | 不得直接触发外部业务 |

这些动作是语义契约；确认授权、候选选择及外部业务执行仍需专门的策略验证，并不因注册了动作名称就完成实现。候选选择目前可由 `answer_pending` 加明确目标表达；暂不新增 `select_option`。任务切换由新动作与状态共同推导，暂不新增 `switch_task`。

## 参数缺失和歧义

目标规则区分以下四种情况，评测应分别标注：

| 情况 | 示例 | 预期处理 |
|---|---|---|
| 必填参数未提供 | 我要退款 | 保留退款目标，策略按顺序询问订单号和原因 |
| 参数存在互斥候选 | 查 A100 或 B200 的物流，记不清了 | 保留一个物流动作；不写入确定订单号；报告 `parameter` 歧义并澄清候选 |
| 任务目标不唯一 | 两个退款任务都存在，用户说继续那个退款 | 报告 `task` 歧义；不随机选任务 |
| 业务用途不明确 | 帮我看看 A100 这个订单 | 报告 `intent` 歧义；不默认查物流 |

缺参不等于用户目标不明确。当前解释器可能在缺参时同时输出 `parameter` 歧义，策略也可以直接从任务必填槽位补问；迁移期间允许这两种表达。它们必须产生等价的目标和参数收集行为。候选冲突则必须显式保留歧义，不能通过实体值掩盖。

明确的新业务可以暂存旧澄清，即使新业务也缺参数。新业务提供的订单号不能回答另一个业务的旧参数问题。任务歧义下，即使模型没有列出候选 ID，策略也会从会话现有任务中构建可供选择的候选，只询问用户，不替用户决定。

`unknown` 是现有兼容兜底标签，不注册为可执行业务意图。业务不明、无关请求、寒暄和模型结构失败也不能等同：前三者需要不同回复策略；结构失败仍然是接口错误。现阶段契约尚未完整区分寒暄和范围外输入，后续迁移可补充逐动作或消息级辅助标记，不能让单一消息级状态阻止其余明确动作被安全处理。

## 放弃流程与撤销真实申请

“不退了”在仅收集资料、尚未产生外部操作时，可以结束本地办理流程。若真实退款已经提交，则需要独立业务目标 `refund.withdraw`，并验证申请状态、权限和外部撤销结果。外部执行结果不确定时先核实，不能仅把本地任务设为 cancelled 就回复撤销成功。

当前没有真实退款服务，也未实现 `refund.withdraw`。接入外部工具前必须增加提交阶段和撤销策略；此边界不得依靠意图名称或 LLM 自行判断是否已执行。

## 多 Agent 关联原则

处理顺序为：消息理解 → 对话策略 → 任务及能力计划 → 编排器 → 工具或 Agent。

注册目录声明能力需求，不保存固定 agent_id。编排器结合权限、任务状态和可用能力选择执行者。`policy.consult` 可以由检索服务完成；一个退款任务也可以在明确需要时申请技术诊断能力。增加 Agent 不自动增加意图类别。

## 候选业务目录

以下 ID 仅作规划，注册解析器拒绝将其当作当前支持的业务：

`refund.status`、`refund.withdraw`、`order.detail`、`order.cancel`、`order.change_address`、`after_sales.exchange`、`after_sales.repair`、`support.complaint`、`support.handoff`。

新增意图需说明用户目标、流程、参数或权限与现有意图的实质区别，并提供正例、反例、易混淆例及多轮回归。近义表达、单个 FAQ 和 Agent 名称不构成新增意图的理由。

## 迁移与验收顺序

1. 已登记目录、别名和边界；任务必填槽位从注册目录读取。目录测试检查语义枚举与注册定义一致。
2. 已统一模型输出、策略输入、API 文档与前端显示的正式 ID。旧动作和旧咨询焦点通过显式别名恢复；任务类型保持稳定。
3. 已生成五份正式标签数据集，迁移清单保存源文件与目标文件 SHA-256；只迁移意图字段，不改变用户原文、业务参数或评分规则。旧评测记录保留。后续仍需完善缺参和候选冲突的独立评测；纯控制消息是否允许 intent 为空，应随目标解析策略一起迁移。
4. 对同一退款任务分别验证资料收集中、待提交、已提交和结果不确定时的取消语义，再接真实工具。
5. 用正式 ID、能力需求、权限和操作计划接入多 Agent 编排，并补充无法路由、能力不可用及跨 Agent 任务引用测试。

迁移脚本为 `evaluation/scripts/migrate_intent_taxonomy.py`，清单为 `evaluation/datasets/taxonomy_v1_migration.json`。历史随机扩展集 v2 的 110/110 仅验证当时接口；正式标签迁移的复测单独归档，不代表未实现业务或未来 Agent 路由已经验证。
