# 意图识别优化与复测对照（2026-10-19）

## 结论

意图解释器的原始 80 条和边界 24 条在最终版本均满足固定约束；对话策略固定语义回归 14/14 轮通过；真实聊天 API 的多轮端到端集 25/25 轮、10/10 场景通过。结果只适用于当前合成开发集和本次模型配置，不代表生产准确率、长期稳定性或真实业务执行安全已经验证。

## 同标签对照

| 版本 | 原 80 条 | 其中合法语义输入 | 边界 24 条 | 原集 HTTP P95 |
|---|---:|---:|---:|---:|
| 基线 v1 | 74/80 | 68/74 | 20/24 | 2788 ms |
| 语义优化 v2 | 79/80 | 73/74 | 24/24 | 3014 ms |
| 语义优化 + 一次结构修复 v3 | 80/80 | 74/74 | 24/24 | 2935 ms |

所有运行均为并发 2、HTTP 不重试，原始数据与标签未修改。边界集在修改提示词前生成并评测；随后作为调试与回归数据，不再属于独立盲测集。每个版本每个样例仅正式运行一次，不提供统计显著性保证。

## 修改内容

1. 查询对象不明确时不得默认猜物流；先报告意图歧义。唯一待回答语境仍可支持裸订单号。
2. 将“或、二选一、记不清”的互斥候选，与“两单都查”的并列独立动作区分；前者保留单个业务动作，候选订单进入参数歧义，不进入实体。
3. 明确参数歧义与多个现有任务歧义的边界；不编造历史 Task ID。
4. 保留对明确新业务、否定、更正、多意图的原有约束。
5. v2 唯一失败为 intent-v1-031 的空工具参数，经 3 次诊断仍复现。v3 对结构非法允许一次显式纠正，纠正后仍执行全部校验；超时和供应商失败不重试。

## 额外调用与耗时

v3 不再保证每个 HTTP 请求只调用一次模型：结构非法时最多两次模型调用，增加费用和潜在延迟。SDK 自动重试仍关闭。原集和边界集的 P95 分别为约 2.93 秒、3.04 秒，不代表纠正请求本身耗时上限。

HTTP 评测器只记录最终 API 响应，无法从每条结果中直接看到供应商原始输出与内部纠正次数。因此最终通过率是**整个解释器（包含一次纠正）的成功率**，不是首次模型输出准确率。运行期间查看了脱敏纠正事件日志，但日志缺少 case_id，不据此推算每类首次失败率。

结构修复不能兜底语义误判；不能将未知任务、无原文实体或其他非法结果默认为成功。离线回归仍包含持续错误时拒绝、伪造引用与实体拒绝的测试。

## 下一阶段：MySQL 持久化与生产 API 工作流

对话策略与归约器首版已经实现并接入聊天 API。下一步按[平台规划](../../docs/zh/PLATFORM_PLAN.md)将进程内状态替换为持久化工作流：

1. 建立 MySQL 会话、任务、消息、状态事件与请求回执表，确保业务事实有唯一权威来源。
2. 在模型请求之外执行原子提交；加入会话版本检查与幂等键，防止重试和并发消息覆盖状态。
3. API 从数据库加载完整的少量活动任务上下文，让服务重启后继续同一会话。
4. 为持久化补充重启恢复、重复请求、版本冲突和事务回滚测试；之后再接真实业务工具。

当前仍为内存会话；评测没有覆盖 MySQL 持久化、身份权限或真实退款/物流执行。
